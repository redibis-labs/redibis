# Redibis Behavior Policy Runtime — Recommended Architecture

**Status:** implemented (open-core Phases 0–9 on branch `plugable_policy`); default
`behavior.enabled: false` so existing flows stay byte-identical.  
**Audience:** engineers and LLM coding agents that have no prior conversation context.  
**Companion implementation plan:** `docs/BEHAVIOR_POLICY_IMPLEMENTATION_PLAN.md`
(see **Implementation status** there for shipped vs remaining gaps).  
**Related current design:** `docs/EDGE_RULES_GUIDE.md`,
`docs/EDGE_RULES_POLICY_IMPL_HANDOVER.md`, `CLAUDE.md`, and `AGENTS.md`.

This document is the design authority for the Behavior Policy Runtime. The runtime
is in-tree under `redibis/behavior/` with PII pipeline integration, REST/CLI
lifecycle, Settings UI, plug-in SDK, and learning helpers. Classification / quality /
profiling / masking adapters ship as library APIs; only the PII path is wired into
`services/pipeline.py` today.

---

## 1. Executive decision

Build a framework-neutral **Behavior Policy Runtime** around Redibis engines.

The runtime evaluates versioned YAML/JSON policies against typed, privacy-safe facts
at explicit engine hook stages. A matching rule produces a typed `BehaviorPatch`.
The engine adapter validates and reduces the patch; policy code never mutates an
engine object directly.

Keep the **operator-facing rule deliberately smaller** than the compiled runtime
model. An operator should reason about only:

```text
Rule { when, effects, reason, priority, terminal }
```

Policy metadata selects the engine, hook, and scope once for the rule group. The
compiler derives authority from the source, fixes unknown-fact behavior to no-match in
v1, fixes incompatible-effect handling to review, and resolves policy layers. These
are enforcement mechanisms, not normal authoring knobs.

Provide two extension tiers:

1. **Product tier — declarative policy**
   - Users author YAML/JSON through a structured editor or raw text.
   - Rules expose `when`, `effects`, `reason`, optional `priority`, and optional
     `terminal`; stable IDs are generated by the editor or supplied in raw YAML.
   - Rules may use only registered facts, operators, and effects.
   - Unknown fields fail closed during validation.
   - Rules cannot import Python, access raw cell values, perform I/O, or write contracts.
   - A v1 linter reports unreachable, shadowed, conflicting, unsupported, and
     unknown-only rules before activation.

2. **Deployment tier — trusted plug-ins**
   - Deployment developers ship normal, preinstalled Python packages.
   - Packages register typed fact providers or action handlers through entry points.
   - User policies refer only to approved registry identifiers.
   - Plug-ins are allow-listed and identified by package/version/source digest.

Do **not** expose inline Python as a normal rule-authoring feature. If generated or
uploaded code is supported in the future, it must use the existing
propose → scan → approve → sandbox process and remain outside the deterministic
core policy format.

The design intentionally preserves these existing invariants:

- The detector produces evidence; the equation/classification layer produces verdicts.
- `ContractStore.upsert()` remains the only contract-bucket writer.
- Passing validators and safety/legal guards outrank user behavior policies.
- LLM output is a proposal unless approved or backed by deterministic policy.
- Operational evidence and audit data remain outside the ODCS contract specification.
- No domain package imports CLI or agent-framework code.

## 2. Problem statement

Redibis combines multiple kinds of engines:

- PII evidence engines: regex/Presidio, NER, phone validation, telecom validators.
- PII equation modes: strict, balanced, lenient, independent.
- Classification policy: tags, co-tags, retention, jurisdiction, approval routing.
- Profiling engines: Great Expectations, OpenMetadata, DuckDB, and plug-ins.
- Quality validators and generated rules.
- Masking-plan suggestion and value-transform engines.
- Agent tools that orchestrate these capabilities.

No engine or model can encode every customer-specific semantic edge case. Examples:

- `lac` and `tac` look phone-like but are network identifiers.
- `customer_id` may look like a national ID but fail its checksum.
- `content_hash` may match a broad password-hash name rule.
- A generated quality rule may be invalid for one table family.
- A profiling triage threshold may need adjustment for a specific data domain.
- A masking recommendation may need a jurisdiction-specific policy.

The product therefore needs a controlled way to express behavior such as:

```text
if column.name matches "(^|_)lac$"
and verdict.entity == "PHONE_NUMBER"
and phone.valid_rate < 0.8
then set verdict.entity = "NETWORK_ID"
and add an audit reason
```

It also needs a trusted extension mechanism for behavior that is too complex for
basic predicates:

```text
if conditions match, invoke the precompiled action
"telecom.normalize_network_identifier"
```

The engine must accept these instructions through a stable object model rather than
requiring users to edit the engine implementation.

## 3. What already exists

The new design should extract and generalize proven patterns; it should not replace
them with a new parallel system.

### 3.1 Declarative edge rules

`redibis/classification/edge_rules.py` already provides:

- allow-listed `when` and `then` keys;
- fail-closed validation;
- deterministic first-match evaluation;
- checksum precedence;
- policy-pack overlays by rule ID;
- a `RefineResult`;
- a `decision_path` marker;
- promotion of a human correction into a draft rule.

Rules are stored in classification policy packs and applied by
`redibis/services/pipeline.py` after `decide_pii()`.

This is the closest starting point for the proposed runtime.

### 3.2 Engine registries

Redibis already uses registries and entry points for several plug-in families:

- profilers: `redibis.profilers`;
- quality validators: `redibis.validators`;
- agent tools: `redibis.agent_tools`;
- NER backends and agent dynamic tools through local registries.

The behavior runtime should use the same registration style for trusted fact and
action extensions.

### 3.3 Per-run configuration overrides

`RegexOverrides`, `RegexSet`, `QualityRuleSet`, `ScanConfig`, and config stores already
separate editable product configuration from engine-facing objects.

The behavior runtime should follow the same pattern:

```text
editable policy document
    → validated immutable BehaviorPolicy
    → engine-facing BehaviorPolicySet
```

### 3.4 Durable human decision overlays

PII, quality, and definition decisions use `_meta/*_decisions` sidecars. They are
reconciled during every `ContractStore.upsert()` because normal contract merging
cannot remove unioned tags or omitted fields.

Behavior policy must not replace these overlays:

- Behavior policy changes scan-time or recommendation-time behavior.
- Decision overlays are authoritative durable human decisions on contract state.

### 3.5 Existing audit channels

Redibis already has:

- immutable contract audit snapshots;
- append-only provenance;
- per-column operational telemetry;
- structured, sanitized decision logs;
- agent audit events and governance transitions;
- human reviewer, timestamp, run, and version fields on decisions.

The new runtime should emit structured events into these channels rather than
inventing an unaudited log.

## 4. Current gaps that justify generalization

### 4.1 Edge rules are tied to PII/classification

The current context, conditions, result, and application code know about
`PIIDetection`. They cannot naturally apply to profiling, quality, masking-plan
suggestions, classification candidates, or agent decisions.

### 4.2 Actions are not uniformly consumed

`RefineResult` can carry `forbid_entity`, `set_classification`,
`set_masking_policy`, and `add_tags`, but the current refinement function directly
applies only a subset of these fields. A rule may therefore validate and match without
having its expected downstream effect.

The generalized design must produce a typed patch and require an adapter to declare
which patch operations it consumes.

### 4.3 Rule order is implicit policy

Current rules are first-match-wins in list order. A broad rule can silently shadow a
specific rule. A generalized runtime needs:

- explicit priority;
- deterministic tie-breaking;
- a declared conflict policy;
- a trace of all matching, skipped, blocked, and shadowed rules.

### 4.4 Configuration promises are not fully enforced

`classification.per_run_overlay_allowed` exists but is not enforced consistently.
Authorization and scope checks must occur at policy load/API boundaries and again at
runtime.

### 4.5 Execution paths can drift

The modern shared pipeline applies edge rules, while legacy Workflow B follows a
different direct detector/equation path. Generalized behavior hooks must be placed in
shared domain entry points or all supported paths must call the same adapter.

### 4.6 Validation is not fully typed

The current rule validator strongly validates keys and regex syntax, but many values
do not have complete type, range, enum, or cross-field validation.

The new format needs structural schema validation plus semantic registry validation.

### 4.7 Audit is partly human-readable text

`decision_path` is useful, but a string is insufficient for replay, conflict analysis,
policy impact reporting, and FP/FN metrics.

## 5. Design principles

### 5.1 Engines expose capabilities, not internals

A policy may read registered facts and request registered actions. It may not access
arbitrary object attributes or mutate engine state.

### 5.2 Patches, not direct mutation

An action returns a `BehaviorPatch`. The engine adapter validates the patch against
its stage capabilities and applies it immutably where practical.

This gives Redibis one place to enforce:

- allowed fields;
- precedence;
- value bounds;
- safety guards;
- review requirements;
- before/after audit capture.

### 5.3 Explicit hook stages

Every rule states where it executes. A rule valid at `post_verdict` cannot silently
run during evidence generation or contract persistence.

### 5.4 Privacy-safe context

Policy context contains column/table semantics, scores, rates, validator outcomes,
types, identifiers, and approved-decision metadata. It does not expose individual
cell values.

An engine may compute aggregate facts from sampled data internally, but the resulting
fact must be typed and privacy-classified before entering policy context.

### 5.5 Deterministic and replayable

The same:

- normalized context;
- policy content SHA;
- registry manifest;
- engine adapter version;

must produce the same patch and trace.

Time, randomness, network access, filesystem access, and mutable process globals are
not available to normal rule actions.

### 5.6 Fail closed

Unknown facts, operators, actions, hooks, enum values, or unsupported patch operations
reject policy activation. Missing runtime facts use explicit three-valued semantics.

### 5.7 Scope limits blast radius

Every policy and rule can be restricted by engine, stage, environment, table pattern,
column pattern, jurisdiction, tenant, effective period, and run mode.

### 5.8 Human authority remains separate

Automated behavior policy can correct repeatable cases. Durable reviewer decisions
remain in authoritative sidecars and outrank automated policies.

## 6. Target architecture

```text
┌───────────────────────────────────────────────────────────────────────────┐
│ Authoring                                                                 │
│ Structured editor / YAML / JSON / approved correction promotion          │
└──────────────────────────────────┬────────────────────────────────────────┘
                                   │
                                   ▼
┌───────────────────────────────────────────────────────────────────────────┐
│ Policy compiler                                                           │
│ Parse → schema validate → registry validate → scope/authz → normalize      │
│ → content SHA → immutable BehaviorPolicySet                               │
└──────────────────────────────────┬────────────────────────────────────────┘
                                   │
                         attached to a scan/run
                                   │
                                   ▼
┌────────────┐   ┌──────────────┐  │  ┌────────────────────────────────────┐
│ Redibis    │──▶│ Engine hook  │──┼─▶│ Behavior Policy Runtime            │
│ engine     │   │ adapter      │  │  │ scope → facts → predicates         │
└────────────┘   └──────────────┘  │  │ → matches → actions → patch        │
      ▲                             │  └──────────────────┬─────────────────┘
      │                             │                     │
      │                  ┌──────────▼──────────┐          │
      │                  │ Fact/operator/action│          │
      │                  │ registries          │          │
      │                  └─────────────────────┘          │
      │                                                   ▼
      │                                      ┌──────────────────────────────┐
      └──────────────────────────────────────│ Patch validator/reducer      │
                                             │ + invariant guards           │
                                             └──────────────┬───────────────┘
                                                            │
                                                            ▼
                                             ┌──────────────────────────────┐
                                             │ Structured audit + metrics   │
                                             │ + optional review item       │
                                             └──────────────────────────────┘
```

### 6.1 Runtime components

1. **Policy parser/compiler**
   - Parses YAML/JSON.
   - Validates the document schema.
   - Resolves registry references.
   - Binds every fact/effect descriptor at compile time.
   - Lints unreachable, shadowed, overlapping, and conflicting rules.
   - Normalizes rule order and defaults.
   - Produces immutable dataclasses and a canonical content digest.

2. **Behavior registry**
   - Stores fact, operator, and action descriptors.
   - Separates metadata from implementation.
   - Merges built-ins and trusted entry-point plug-ins.
   - Built-in identifiers win on collisions unless an explicit namespaced policy says
     otherwise.

3. **Engine hook adapter**
   - Builds a `BehaviorContext`.
   - Declares allowed facts/actions/patch operations for one engine and stage.
   - Applies the reduced patch to the engine-owned object.

4. **Policy evaluator**
   - Filters policies/rules by scope and hook.
   - Evaluates conditions with three-valued logic.
   - Resolves priority and conflicts.
   - Calls action handlers.
   - Returns patches and a complete trace.

5. **Patch validator/reducer**
   - Verifies operation schemas and target capabilities.
   - Applies precedence and invariant guards.
   - Combines compatible operations deterministically.
   - Rejects or routes conflicts to review.

6. **Audit sink**
   - Emits a sanitized, structured event.
   - Never embeds raw values in the contract.
   - Links event, policy digest, run, engine stage, and resulting contract version.

## 7. Hook model

Use a small, stable hook vocabulary:

| Hook | Purpose | Example permitted changes |
|---|---|---|
| `pre_evidence` | Configure an engine invocation | choose approved recognizers, bounded run options |
| `post_evidence` | Refine evidence/candidates | suppress collision, add candidate, adjust bounded score |
| `pre_verdict` | Influence verdict strategy | select equation mode, adjust scoped threshold |
| `post_verdict` | Correct a produced verdict | set entity, promote/demote, require review |
| `pre_action` | Refine a proposed downstream action | alter masking recommendation, suppress quality proposal |
| `post_action` | Validate/escalate result | add warning, require approval, block unsafe action |

Not every engine supports every hook. `EngineBehaviorAdapter.capabilities()` declares
the valid combinations.

### Why not one universal hook?

A universal hook makes it easy to bypass the evidence/verdict separation, execute
actions before required validation, or mutate contract state directly. Explicit stages
make precedence and ownership testable.

## 8. Recommended object model

The following is conceptual Python. Exact module placement is defined in the companion
implementation plan.

```python
JSONValue = None | bool | int | float | str | list["JSONValue"] | dict[str, "JSONValue"]

# Small public authoring model. Engine/hook/scope live on the policy.
@dataclass(frozen=True)
class AuthoredRule:
    id: str
    when: ConditionNode
    effects: tuple["EffectCall", ...]
    reason: str
    priority: int = 100
    terminal: bool = False

@dataclass(frozen=True)
class BehaviorPolicy:
    id: str
    version: str
    description: str
    engine: str
    stage: HookStage
    scope: RuleScope
    rules: tuple[AuthoredRule, ...]
    content_sha256: str
    source: PolicySource

# Internal compiled model. Authors do not set these enforcement fields.
@dataclass(frozen=True)
class CompiledRule:
    id: str
    stage: HookStage
    priority: int
    scope: RuleScope
    condition: ConditionNode
    effects: tuple["EffectCall", ...]
    reason: str
    terminal: bool
    authority: Authority
    on_unknown: UnknownBehavior = UnknownBehavior.NO_MATCH  # fixed in v1
    conflict_policy: ConflictPolicy = ConflictPolicy.REVIEW  # fixed in v1
    source_layer: str = ""

@dataclass(frozen=True)
class RuleScope:
    engines: tuple[str, ...] = ()
    tables: tuple[str, ...] = ()
    columns: tuple[str, ...] = ()
    environments: tuple[str, ...] = ()
    jurisdictions: tuple[str, ...] = ()
    effective_from: str | None = None
    effective_until: str | None = None

@dataclass(frozen=True)
class Predicate:
    fact: str
    operator: str
    expected: JSONValue

@dataclass(frozen=True)
class ConditionGroup:
    kind: Literal["all", "any", "not"]
    children: tuple["ConditionNode", ...]

ConditionNode = Predicate | ConditionGroup

@dataclass(frozen=True)
class EffectCall:
    effect: str
    params: dict[str, JSONValue]

@dataclass(frozen=True)
class BehaviorContext:
    run_id: str
    table: str
    column: str | None
    engine: str
    stage: HookStage
    facts: Mapping[str, JSONValue]
    capabilities: "BehaviorCapabilities"
    registry_manifest_sha256: str

@dataclass(frozen=True)
class PatchOperation:
    op: str
    path: str
    value: JSONValue
    authority: Authority
    reason: str

@dataclass(frozen=True)
class BehaviorPatch:
    operations: tuple[PatchOperation, ...] = ()
    require_review: bool = False
    review_role: str | None = None
    reasons: tuple[str, ...] = ()

@dataclass(frozen=True)
class EvaluationTrace:
    policy_sha256: str
    evaluated_rules: tuple["RuleTrace", ...]
    proposed_patch: BehaviorPatch
    applied_patch: BehaviorPatch
    blocked_operations: tuple["BlockedOperation", ...]
```

### Object-model decisions

- Use immutable dataclasses in the core.
- Keep `AuthoredRule` separate from `CompiledRule`. Runtime rigor must not become
  authoring complexity.
- Keep policy documents JSON/YAML-safe.
- Do not serialize callable objects into policies.
- Registry identifiers are namespaced strings, for example
  `core.verdict.set_entity` or `telecom.normalize_network_identifier`.
- Derive `authority`, `on_unknown`, `conflict_policy`, and source-layer precedence in
  the compiler; do not expose them as normal v1 rule fields.
- Keep facts in a flat namespaced map to simplify schema evolution and audit, but
  expose typed descriptor metadata for validation and UI generation.
- Keep patch operations domain-neutral at the core and constrain paths through
  adapter capabilities.

## 9. Policy document format

Recommended YAML:

```yaml
apiVersion: redibis.io/behavior-policy/v1
kind: BehaviorPolicy
metadata:
  id: telecom-corrections
  version: "1.0.0"
  description: Correct known telecom identifier edge cases.
  owner: data-governance
appliesTo:
  engine: pii
  stage: post_verdict
  environments: [production]
  tables: ["cdr.*"]
rules:
  - id: network-id-not-phone
    priority: 200
    when:
      all:
        - fact: column.name
          op: matches
          value: "(?i)(^|_)(lac|tac)$"
        - fact: verdict.entity
          op: eq
          value: PHONE_NUMBER
        - fact: validators.phone.valid_rate
          op: lt
          value: 0.8
    effects:
      - effect: core.verdict.set_entity
        params:
          entity: NETWORK_ID
    reason: Network identifier, not a phone number.
    terminal: true
```

### 9.1 Authoring semantics in v1

The public model has one ordering mechanism: higher `priority` evaluates first. The
structured editor should normally present this as rule order and generate numeric
priorities; raw-YAML authors may set the number directly.

Semantics:

1. Matching effects accumulate when compatible.
2. A matching `terminal: true` rule stops lower-priority rules.
3. Missing facts mean no match.
4. Incompatible scalar effects route to review.
5. Authority comes from policy source and cannot be authored.
6. Built-in/global/table/run layering is compiled before evaluation and is not a
   per-rule control.

`reason` is mandatory, non-empty, and belongs to the rule itself. It explains why the
rule exists and is copied into every match, patch, simulation result, and audit event.
An effect such as `core.review.add_reason` may add situational detail, but it never
replaces the rule rationale.

### 9.2 V1 linting is an activation gate

Linting must ship with the compiler/runtime, not wait for the later visual editor.
The validation and simulation APIs return lint results from the first product release.

Required checks:

- unreachable or fully shadowed rule;
- terminal rule shadowing lower-priority rules;
- duplicate/equivalent condition;
- same-priority incompatible scalar effects;
- broad rule taking precedence over a narrower rule;
- fact unavailable at the selected engine/hook;
- effect unsupported by the selected engine/hook;
- overlapping policy scopes with conflicting effects;
- rule that can only evaluate to unknown;
- missing reason;
- unnecessary custom effect where a built-in effect exists.

Errors block activation. Conflicts block activation. Shadowing requires explicit
acknowledgement and a successful simulation. Other overlap warnings require simulation.

### Format limits

The compiler should enforce configurable hard limits:

- maximum document size;
- maximum policies and rules per run;
- maximum condition-tree depth and node count;
- maximum actions per rule;
- maximum regex length and safe execution budget;
- maximum string/list/map sizes in parameters;
- no duplicate policy or rule IDs in the effective set.

These limits prevent denial-of-service through apparently valid configuration.

## 10. Fact registry

Each fact descriptor should contain:

```python
@dataclass(frozen=True)
class FactDescriptor:
    id: str
    value_type: str
    description: str
    supported_engines: tuple[str, ...]
    supported_stages: tuple[HookStage, ...]
    privacy_class: Literal["public", "metadata", "sensitive_aggregate"]
    stability: Literal["stable", "experimental"]
    nullable: bool
```

Examples:

- `column.name`
- `column.logical_type`
- `column.is_numeric`
- `profile.null_rate`
- `profile.cardinality_ratio`
- `evidence.regex.score`
- `evidence.ner.score`
- `validators.luhn.status`
- `validators.phone.valid_rate`
- `verdict.detected`
- `verdict.entity`
- `verdict.confidence`
- `classification.tags`
- `quality.rule.expectation_type`
- `masking.suggested_strategy`
- `review.prior_status`

### Raw-value rule

No fact may contain raw cell values. A trusted fact provider may inspect an
engine-owned sample only to produce a bounded aggregate such as a checksum pass rate.
The fact descriptor must classify that aggregate and the audit sanitizer must allow it.

## 11. Operator registry and condition semantics

Built-in operators should cover most user needs:

- equality: `eq`, `neq`;
- ordering: `lt`, `lte`, `gt`, `gte`, `between`;
- membership: `in`, `not_in`, `contains`, `contains_any`, `contains_all`;
- strings: `matches`, `starts_with`, `ends_with`;
- existence: `exists`, `is_null`;
- booleans: `is_true`, `is_false`.

Operators declare supported input and expected-value types.

### Three-valued logic

Predicates evaluate to `TRUE`, `FALSE`, or `UNKNOWN`.

`UNKNOWN` occurs when:

- a fact is unavailable because an engine did not run;
- a profile did not compute a metric;
- a value is null and the operator does not define null behavior.

In v1, `UNKNOWN` always means no-match. Authors do not choose another behavior per
rule. The compiled model retains an internal unknown-policy seam for a future API
version, but adding author choices requires evidence that no-match plus linting is
insufficient.

## 12. Effect registry and trusted plug-ins

Authors select **effects**. An effect may be a built-in patch constructor or a trusted
precompiled action behind a registered effect ID. This keeps the rule vocabulary
consistent while preserving the deployment extension point.

An effect descriptor should include:

```python
@dataclass(frozen=True)
class EffectDescriptor:
    id: str
    description: str
    params_schema: dict
    supported_engines: tuple[str, ...]
    supported_stages: tuple[HookStage, ...]
    patch_operations: tuple[str, ...]
    side_effect: Literal["none", "review", "write", "external"]
    autonomy: Literal["auto", "suggest-only", "gate"]
```

Handler protocol:

```python
class BehaviorAction(Protocol):
    descriptor: EffectDescriptor

    def apply(
        self,
        context: BehaviorContext,
        params: Mapping[str, JSONValue],
    ) -> BehaviorPatch:
        """Return a deterministic patch; perform no direct mutation or I/O."""
```

Recommended entry-point groups:

- `redibis.behavior_facts`
- `redibis.behavior_actions`

### Plug-in loading rules

- Plug-ins are installed by deployment administrators, not uploaded by ordinary users.
- Plug-in IDs must be namespaced.
- Manifests include distribution name, version, entry point, and source/package digest
  where available.
- An allow-list controls which plug-ins may load.
- Built-in IDs cannot be replaced by third-party packages.
- An effect that declares `write` or `external` cannot auto-run from normal behavior
  policy; it must route through an existing approved/gated tool.
- Core and domain packages must not import plug-in implementations.

### Why precompiled plug-ins instead of inline Python?

Normal packages can be reviewed, tested, signed, pinned, scanned, rolled back, and
deployed through existing software controls. Inline Python inside a policy document
would mix configuration and code, weaken replay, expose data, and bypass dependency
and approval controls.

## 13. Patch validation and reduction

Effects return proposals. The patch reducer determines what can be applied.

Example operations:

```text
verdict.set_detected
verdict.set_entity
verdict.set_confidence
evidence.add_candidate
evidence.drop_candidate
threshold.set_for_run
equation.select_for_run
classification.add_candidate_tag
quality.suppress_proposal
masking.set_suggested_strategy
review.require
review.add_reason
```

### Capability declaration

Each adapter publishes:

```python
BehaviorCapabilities(
    readable_facts={...},
    allowed_actions={...},
    allowed_patch_operations={...},
    immutable_paths={...},
    value_constraints={...},
)
```

### Reduction rules

1. Reject operations unsupported by the adapter/stage.
2. Reject operations that violate value schemas or bounds.
3. Apply authority precedence.
4. Preserve safety and validator invariants.
5. Detect incompatible operations targeting the same path.
6. Route incompatible scalar verdict/security operations to review in v1.
7. Emit proposed, applied, and blocked operations in the trace.

`ConflictPolicy` remains an internal model seam for future versions, but v1 does not
ask operators to select one. Additive reasons/tags/candidates combine deterministically.

## 14. Authority and precedence

Use a first-class `Authority` enum rather than implicit call order:

1. `SAFETY_GUARD`
2. `AUTHORITATIVE_VALIDATOR`
3. `HUMAN_DECISION`
4. `APPROVED_POLICY`
5. `ENGINE_NATIVE`
6. `LLM_PROPOSAL`

Rules:

- Lower-ranked authority cannot override higher-ranked authority.
- A passing authoritative validator may block a conflicting policy operation.
- A human decision overlay wins over future automated scans until removed.
- LLM/memory output cannot auto-override an approved deterministic policy.
- Lawful intercept or equivalent protected states escalate and cannot be applied by
  behavior policy.

The trace must record a blocked operation and the authority that blocked it.
Authority is runtime metadata derived from the engine, validator, human overlay, policy
source, or LLM source. It is not a rule-authoring field.

## 15. Policy scope, composition, and overlays

### 15.1 Scope levels

Support these layers:

1. packaged built-in policies;
2. deployment/global policies;
3. tenant/domain policies;
4. table-family policies;
5. run-specific overlays.

### 15.2 Composition

Compile all active layers into an `EffectivePolicySet`.

Recommended merge rules:

- A rule ID is unique within a policy.
- A higher-precedence layer may replace or disable a lower-layer rule only by fully
  qualified `(policy_id, rule_id)`.
- New rules append to the effective set and are then sorted by priority and stable ID.
- Replacements are validated as complete rules; do not deep-merge arbitrary fragments.
- Every replacement records the base policy SHA and overlay SHA.

Layering is an operator/deployment configuration concern, not a rule-level ordering
mechanism. The compiler must expose the effective rule order and shadowing report so an
author does not need to mentally simulate overlays.

### 15.3 Scope authorization

`per_run_overlay_allowed` and equivalent settings must be enforced:

- when the API accepts the overlay;
- when the run configuration is built;
- when the runtime compiles the effective policy.

This defense-in-depth prevents a lower-level caller from bypassing product controls.

## 16. Audit, provenance, and storage

### 16.1 Policy storage

Behavior policies are operational configuration, not ODCS contract content.

Use a config-store namespace such as:

```text
behavior-policies/{policy_id}/{version}.yaml
behavior-policies/{policy_id}/active.json
```

Local development can use a corresponding configurable directory.

### 16.2 Structured execution event

```python
@dataclass(frozen=True)
class PolicyAuditEvent:
    event_id: str
    ts: str
    run_id: str
    table: str
    column: str | None
    engine: str
    stage: str
    policy_id: str
    policy_version: str
    policy_sha256: str
    rule_id: str
    action_ids: tuple[str, ...]
    actor: str
    context_hash: str
    before_hash: str
    proposed_patch: dict
    applied_patch: dict
    blocked_operations: tuple[dict, ...]
    outcome: str
    duration_ms: float
```

Store or route this through operational telemetry/run artifacts, not the contract spec.
The event must be sanitized using the same no-raw-value principle as
`redibis.obs.decision`.

### 16.3 Contract linkage

When a policy-influenced result reaches `ContractStore.upsert()`:

- provenance records the behavior policy ID/version/SHA;
- per-column telemetry may record the applied rule IDs;
- the contract audit snapshot remains the durable before/after contract record.

No behavior action writes the contract directly.

### 16.4 Policy lifecycle audit

Policy create, validate, simulate, approve, activate, deactivate, and rollback events
should record:

- actor and role;
- timestamp;
- previous and new SHA;
- approval note;
- simulation report reference;
- effective scope.

### Simulation

Simulation should run on sanitized stored contexts or a newly generated context without

- before/after verdicts;
- aggregate affected columns;
- comparison against labelled or human-reviewed outcomes where available;
- lint findings and the effective rule order after policy layering.

Activation should require simulation for production-scoped policies.

## 18. Engine integration model

### 18.1 PII

Initial adapter:

```text
detect_pii() → post_evidence hook → bounded pre_verdict hook
             → decide_pii() → post_verdict hook
```

Facts reuse `PIIDetection`, `Thresholds`, profile aggregates, and checksum/phone
validator outcomes.

The adapter converts legacy `edge_rules` into the generalized policy object so existing
packs preserve behavior during migration.

The first authoritative PII release must include one bounded false-negative lever:
`threshold.set_for_run`. It is clamped by adapter-owned hard minimum/maximum values,
applies only to the scoped run, and requires review when it promotes a previously
negative verdict. This prevents the first release from claiming FP/FN tuning while
supporting only post-verdict false-positive correction.

Fact providers should bind to values already computed by detection/profile stages.
They must not recompute checksums, phone rates, or profile metrics during policy
evaluation when the existing result already carries them.

At scan time, the reducer should consult relevant human decision overlays so the trace
shows an automated policy operation being blocked early. Reconciliation in
`ContractStore.upsert()` remains the authoritative write-time backstop.

Do not set `detected=True` inside `detect_pii()`.

### 18.2 Classification

Hooks:

```text
ensemble candidates → post_evidence
policy resolve → post_verdict
approval routing → post_action
```

Policies may add/drop candidates or require review. Safety-forbidden tags and approval
escalations remain higher authority.

### 18.3 Quality

Hooks apply to proposed or evaluated quality rules, not arbitrary GE internals.

Permitted examples:

- suppress a generated proposal for a scoped table family;
- change severity;
- require review;
- invoke a registered domain quality action.

Durable manual/suppressed contract rules continue through `QualityDecisionStore`.

### 18.4 Profiling

Start with triage and recommendation hooks, not mutation of profiler output internals.

Permitted examples:

- require deep profiling for a scoped column;
- adjust a bounded triage threshold for a run;
- select an installed profiler engine before execution.

### 18.5 Masking

Policy may change a **suggested masking plan** or require approval. It does not bypass
the masking engine, expose keys, or enforce policy externally.

Actions that transform values remain in `MaskingEngine` and existing gated workflows.

### 18.6 Agent tools

Agents may select a policy pack or propose a policy. They call the typed behavior API;
they do not import engine libraries or action implementations.

LLM-proposed policies remain suggest-only until validation, simulation, and approval.

## 19. Safety and security model

### 19.1 Threats

- code injection through rule content;
- regex denial of service;
- raw-data exfiltration through facts or audit;
- policy that bypasses a validator;
- privilege escalation through run overlays;
- plug-in name collision or supply-chain replacement;
- nondeterministic plug-in behavior;
- excessive rules causing scan latency;
- direct contract mutation outside the single writer.

### 19.2 Controls

- no `eval`, `exec`, imports, or expressions in declarative policies;
- JSON Schema/Pydantic structural validation;
- registry-based semantic validation;
- safe/bounded regex handling;
- size/depth/count/time budgets;
- privacy classification on facts;
- sanitized context and audit;
- explicit authority precedence;
- role-based policy lifecycle actions;
- immutable content SHA and version pinning;
- plug-in allow-list and manifest digest;
- patch capability enforcement;
- simulation and staged activation;
- circuit breaker: disable behavior runtime globally or per engine;
- no contract-writer capability in actions.

### 19.3 Runtime failure visibility

For an ordinary evaluator failure, the safe availability default is to preserve the
baseline engine result. This must never be silent: the run is marked with a visible
behavior-policy warning containing the affected policy/rule, engine stage, target, and
fallback outcome. The warning appears in library/service results, CLI/web progress or
summary output, run artifacts, and structured audit/metrics.

A policy may be activated in a stricter policy-level `fail_run` mode when silently
reintroducing a known false positive/negative is less acceptable than failing the
governed run. Safety/legal guard failures remain fail closed regardless of this setting.

## 20. Performance model

The runtime executes per column or per proposal, so its budget must be bounded.

Recommended optimizations:

- compile policies once per effective policy SHA;
- precompile safe regexes;
- index rules by engine, stage, and simple scope;
- lazily compute facts only when referenced;
- cache pure fact-provider results within one run/context;
- evaluate cheap predicates before expensive predicates;
- cap runtime per context and record timeout;
- expose match/error/latency metrics by policy and rule.

The runtime must have a no-policy fast path with negligible overhead.

## 21. Compatibility and migration

### Phase A — stabilize current behavior

- Add complete value validation to edge rules.
- Ensure all declared current actions are either applied or rejected.
- Enforce per-run overlay configuration.
- Add structured traces.
- Converge modern and legacy PII paths.

### Phase B — compatibility adapter

- Convert `ClassificationPolicy.edge_rules` into `BehaviorPolicy`.
- Preserve current rule IDs, order semantics, checksum protection, and
  `decision_path`.
- Ship structural/semantic linting and effective-order/shadow reports before activation.
- Run old and new evaluators in shadow mode and compare output.

### Phase C — make the generalized runtime authoritative

- Switch PII post-verdict corrections and the bounded pre-verdict threshold effect to
  the new adapter after parity tests.
- Keep the old YAML shape supported for a deprecation period.
- Export normalized v1 behavior policy from the pack editor.

### Phase D — add other engine adapters

- Classification candidates.
- Quality proposals.
- Profiling triage.
- Masking recommendations.

Do not add all domains before PII parity and auditability are proven.

## 22. Alternatives considered

### 22.1 Inline Python rules

**Rejected for the product tier.**

Benefits:

- maximum flexibility;
- familiar syntax;
- easy access to existing Python functions.

Costs:

- code execution and exfiltration risk;
- nondeterminism;
- difficult static validation;
- difficult UI generation;
- unstable dependence on internal object shapes;
- unclear precedence and mutation ownership;
- weak replay and rollback;
- deployment and dependency complexity.

Use trusted preinstalled plug-ins for the legitimate extension need.

### 22.2 Free-form expression language

**Rejected initially.**

An expression language eventually becomes another programming language requiring a
parser, type system, sandbox, debugger, and compatibility policy. The proposed boolean
condition tree plus registered operators covers the current use cases more safely.

Reconsider only if real policies cannot be expressed without repeated custom actions.

### 22.3 One generic dictionary passed to callbacks

**Rejected.**

It gives weak compatibility guarantees, poor documentation, and arbitrary mutation.
Use typed descriptors, immutable context, and patches.

### 22.4 Fork each engine or subclass it

**Rejected as the user-facing model.**

Subclassing is appropriate for full engine plug-ins such as profilers, but it is too
heavy for small policy changes and causes customer forks of base behavior.

### 22.5 Put overrides directly in contracts

**Rejected.**

Behavior configuration is operational control, not ODCS desired-state content.
Contracts should contain resulting policy intent; telemetry and rule execution belong
in sidecars/audit.

### 22.6 Reuse only the current edge-rule module

**Insufficient long-term.**

It is a good compatibility source but couples context and result to PII/classification.
A neutral core plus domain adapters gives reuse without weakening domain boundaries.

## 23. Locked decisions and clarifications

These decisions should be treated as the default unless a product owner explicitly
changes them.

1. **Two tiers:** declarative product policies and deployment-owned code plug-ins.
2. **No inline Python** in policy YAML/JSON.
3. **No raw cell values** in `BehaviorContext`, policy audit, or memory.
4. **Immutable policy versions** identified by canonical SHA-256.
5. **Explicit hook stages** instead of one universal callback.
6. **Actions return patches** and do not mutate domain objects directly.
7. **Human overlays outrank automated policy.**
8. **Validators/safety guards outrank behavior policy.**
9. **V1 conflict handling is fixed to review** for incompatible verdict/security
   changes; authors do not choose a conflict policy.
10. **V1 unknown-fact handling is fixed to no-match**; authors do not choose it per rule.
11. **Policy configuration stays outside ODCS contracts.**
12. **All contract effects use existing writers and overlays.**
13. **LLM-proposed policies are suggest-only** until approved.
14. **PII is the first migration target:** post-verdict correction plus one bounded
    pre-verdict threshold effect.
15. **Existing edge-rule packs remain compatible** during migration.
16. **The public rule model is** `when + effects + reason + priority + terminal`;
    authority and layering remain compiler/runtime concerns.
17. **Lint and shadowed-rule analysis ship in v1** and gate activation.
18. **The first PII release includes a bounded pre-verdict threshold effect** so both
    FP and FN tuning are represented.

## 24. Open product decisions

The design does not require immediate answers; the implementation plan carries safe
defaults.

1. **Tenancy model**
   - Question: Is one Redibis deployment single-tenant or must policy ownership isolate
     multiple organizations?
   - Default: include optional `tenant` in scope and audit, but do not require it.

2. **Production approval roles**
   - Question: Which role can activate global or production policy?
   - Default: Steward for normal behavior; DPO/SecOps/Legal when actions or facts require
     those routes.

3. **Policy storage backend**
   - Question: local/S3 config store only, or database-backed lifecycle records?
   - Default: reuse config-store abstraction; keep the runtime independent of backend.

4. **Safe regex implementation**
   - Question: use a timeout-capable regex package, a restricted regex subset, or process
     isolation?
   - Default: abstract regex operator implementation; do not claim length alone is safe.

5. **Historical simulation corpus**
   - Question: which reviewed runs can be retained and for how long?
   - Default: retain only normalized, value-free contexts and labels.

6. **Automatic rollout**
   - Question: support percentage/canary activation in the first release?
   - Default: support `disabled`, `shadow`, and `active`; defer percentage rollout.

7. **Third-party plug-in signing**
   - Question: is package allow-listing enough for open core?
   - Default: allow-list plus package/version/digest; leave cryptographic signing as an
     enterprise deployment option.

8. **Cross-rule aggregation**
   - Question: should multiple compatible rules apply?
   - Default: evaluate all by priority; combine compatible additive operations; stop only
     when `terminal: true`; incompatible scalar effects route to review.

## 25. Success criteria

The architecture is successful when:

- users can correct recurring false positives/negatives without changing engine code;
- behavior is identical when the runtime is disabled;
- every applied change identifies policy, version, SHA, rule, action, and before/after;
- a policy can be simulated, approved, activated, deactivated, and rolled back;
- the same context and policy manifest replay deterministically;
- no policy or plug-in can bypass contract writers, validators, safety rules, or approval;
- existing edge-rule behavior passes parity tests;
- new engine integrations use adapters rather than imports into the neutral core;
- runtime overhead is bounded and observable;
- user-authored content never executes as Python;
- every rule carries a mandatory rationale into simulation and audit;
- baseline fallback after evaluator failure always creates a caller-visible degraded-run
  warning, not only a log or metric.
